# 推迟的事必须带前提，因为"将来有用"本身会过期

- 背景：从 DeepSeek harness 借来的五项设计（按 diff 选最小证据集、负控、删东西六问、invocation 一致性守卫、评审证据生成技能）都属于"现在不做、将来再说"。用户提出的关键风险是：**将来真到那一刻，它可能已经没用了**——所以机制不能只是"到点提醒"，还得逼着将来的 AI 基于那时的现实重新判断，而不是照抄今天写下的理由。
- 决定：`docs/plan/parked.md` 每条必须四行——`条件`、`复核`、`前提`、`判断依据`，由 `scripts/check-parked-triggers.mjs` 机检。
  - `条件` 是文件系统可观测的触发（`<glob> >= n`、`path_exists`），或诚实写作 `仅复核`：没有可观测信号时**不许编造代理指标**。
  - `复核` 是 `review_by <日期>`，兜住"条件一直不成立"的僵尸条目。
  - `前提` 把今天之所以认为"将来会需要"的那个判断写成**可被现实推翻的句子**；红的时候提示语第一行就是把它打印出来，要求先检验前提再决定。
  - 到点只有三种处理：做 / 改条件并写新事实 / 作废（并在 `rejected/` 留一条）。"留着以后再说"不是选项。
- 被拒绝的替代方案：
  - **只写一份 markdown 清单，靠 AGENTS.md 提醒 AI 记得看。** 提醒不是机制：没有东西在条件成立时变红，条目就会永远躺在那里，而且没人知道自己漏了。
  - **为不可观测的触发编造代理（比如用包数代替"出现第二批异步问题"）。** 假精确会让守卫在错误的时刻变红，比不变红更糟。
  - **把待采用清单留在 `master-plan.md` 的表格里。** plan 是按顺序要做的东西；"也许永远不做"混进去之后，plan 就再也无法用来判断进度。清单已迁走，plan 里只留指针。
- 后果：五条 DeepSeek 条目全部有了到期或被叫醒的时刻（最近一条 2026-12-15，最远 2027-06-01）；`check:parked` 进 `check` 链与 `pre-commit`，约 0.1 秒。代价是新增一条守卫的维护面，以及"日期到了就得处理"的摩擦——这是有意的：摩擦正是防止忘记的机制。
