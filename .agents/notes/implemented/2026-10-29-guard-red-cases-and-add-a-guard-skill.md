# 守卫补齐红例，并把"加守卫"固化成 skill

- 背景：`docs/structure.md` §13 立着一条纪律"守卫必须带反例测试"，而两条守卫（`check-ts-relative-imports`、`check-entry-graphs`）做不到——它们把仓库根钉死在脚本目录的上一级，临时夹具驱动不了。同时 `check-doc-links` 上线后第一次跑就拦到一条真断链，说明"文档里的路径断言"是可机检的，而另一类断言（数量）也漂过四次。
- 决定：
  1. `check-entry-graphs` 的根改为可注入（`NAVETI_CHECK_ROOT`），夹具镜像仓库相对路径；`check-ts-relative-imports` 本来就用 `process.cwd()`，直接建临时目录测。两条各补 4 个用例，其中含"超预算""命中禁止路径""预算指向已不存在的 export"这类会红的断言。
  2. 新增 `check-doc-counts`，**只挡真正漂过的三种句式**（`现有 N 个/条`、`N 个脚本/守卫/工作流/生成器/测试文件`、旧的存在性标记），并把 `docs/migration/` 排除在外——那份文档的工作就是数数。
  3. 把加守卫的正确形状写成 `.agents/skills/add-a-guard/SKILL.md`：先写红例命令、根可注入、平台中立、登记四处、验收是"拦到过哪次事故"。
- 被拒绝的替代方案：
  - **给两条守卫补"跑真实仓库断言 exit 0"的测试**。那不是反例测试，是把假绿写进门禁。
  - **通用散文检查**（扫所有路径引用、扫所有数量表述）。第一次试写就命中了项目口号"一个功能一个包"，这种误报的结局是被人关掉，比没有守卫更糟。
  - **把数量做成生成物**。生成 `paths` 已被明确拒绝（§13），生成文档同理：它把"忘了改文档"变成"忘了跑脚本"。
- 后果：`§13` 的"已知缺口"段落被删掉，"每条守卫都有红例"第一次成为成立的说法；`pnpm check` 从 46 项测试涨到 59 项。四个注入实验（真实仓库上注入违规、守卫 exit 1、还原后 `git status` 干净）是这条说法的证据。代价是加守卫的登记面扩大到四处，漏一处就是下一个漂移点——所以 skill 把它写成硬步骤。
