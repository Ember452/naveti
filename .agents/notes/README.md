# 决策记录

一条决定一个文件，命名 `<YYYY-MM-DD>-<slug>.md`。四态目录，状态就是它所在的位置：

| 目录 | 含义 | 何时移走 |
| --- | --- | --- |
| `proposed/` | 已写下、还没定 | 定了就移到 `implemented/` 或 `rejected/` |
| `implemented/` | 已生效 | 被后来的决定取代时移到 `archived/` |
| `archived/` | 被取代，保留不删 | 永不删除 |
| `rejected/` | 被拒绝 + 理由 | 永不删除 |

## 字段（固定四个）

```
# <标题>

- 背景：当时遇到了什么，为什么需要现在决定
- 决定：做了什么，边界在哪
- 被拒绝的替代方案：哪个方案、为什么不要
- 后果：代价、约束、将来什么情况下该重新考虑
```

## 什么时候写

只在**改了边界**时写：新增顶层目录、改依赖方向、改内核语义（`KERNEL.md` §2 的 B 档）、新增 seat、新增守卫、改"什么算绿"、换包管理器或构建形态。

普通功能设计写功能 README；`docs/` 的规则改动直接改文档，不在这里记。

## 与 `docs/` 的分工

`docs/` 写"现在成立的事实与规则"，会随代码更新；这里写"某天为什么选了这条路"，**只追加、不改写**。被推翻时不要改原文，写一条新的并把旧的移到 `archived/`。

## 为什么值得写

`rejected/` 比其余三栏加起来都值钱：被拒绝的方案与理由，是唯一能防止同一个争论重复半年的东西。
