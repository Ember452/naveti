过去三年里，我一直在用 LLM 辅助编程。如果你在读这篇文章，你大概率经历了同样的演进历程：从把代码复制粘贴进 ChatGPT，到 Copilot 自动补全（对我来说从来没好用过），再到 Cursor，最后是新一代编码智能体框架（harness）——Claude Code、Codex、Amp、Droid 和 opencode——它们在 2025 年成了我们的日常主力工具。

我的大部分工作更偏爱 Claude Code。在用了一年半的 Cursor 之后，今年四月份我第一个尝试的就是它。那时候它要朴素得多，这恰好契合我的工作流，因为我是个喜欢简单、可预测工具的简单家伙。然而在过去几个月里，Claude Code 已经进化成一艘宇宙飞船，其中 80% 的功能我根本用不上。而且每次发版，系统提示词和工具集都会变，这会破坏我的工作流，还会改变模型行为。我讨厌这样。另外，它的界面还会闪烁。

这些年来我还构建过各种复杂度不一的智能体。比如 Sitegeist，我那个小小的浏览器操作智能体（browser-use agent），本质上就是一个生活在浏览器里的编码智能体。在所有这些工作中，我学到了一点：上下文工程（context engineering）至关重要。精确控制进入模型上下文的内容能带来更好的输出，尤其是写代码的时候。而现有的框架会在你背后注入一些内容，甚至不在 UI 中显示出来，让这种精确控制变得极其困难甚至不可能。

说到"显示出来"，我想审查自己与模型交互的每一个方面，但基本上没有哪个框架允许你这么做。我还想要一个文档清晰的会话格式，可以自动做后处理，以及一种简单的方式在智能体核心之上构建替代 UI。虽然现有框架部分支持这些，但它们的 API 闻起来就像"有机进化"的产物——这些方案一路上积累了各种历史包袱，这清楚地体现在开发者体验上。我不是在怪罪任何人。如果有无数人在用你的东西，而你需要保持某种向后兼容，这就是你必须付出的代价。

我还折腾过自托管模型，既在本地也在 DataCrunch 上。虽然 opencode 这类框架支持自托管模型，但通常效果不好，主要是因为它们依赖 Vercel AI SDK 之类的库，而这类库不知为何与自托管模型配合得不好，尤其是在工具调用方面。

那么，一个对着 Claude 大喊大叫的老家伙能做什么呢？他会自己写一个编码智能体框架，并给它起一个完全没法用 Google 搜到的名字，这样就永远不会有用户，也就意味着 GitHub issue 区永远不会有 issue。这能有多难？

为了实现这个目标，我需要构建：

- **[pi-ai](https://github.com/badlogic/pi-mono/tree/main/packages/ai)**：一个统一的 LLM API，支持多提供商（Anthropic、OpenAI、Google、xAI、Groq、Cerebras、OpenRouter 以及任何 OpenAI 兼容端点）、流式输出、基于 TypeBox schema 的工具调用、思考/推理支持、无缝的跨提供商上下文交接，以及 token 和成本追踪。
- **[pi-agent-core](https://github.com/badlogic/pi-mono/tree/main/packages/agent-core)**：一个处理工具执行、校验和事件流的智能体循环。
- **[pi-tui](https://github.com/badlogic/pi-mono/tree/main/packages/tui)**：一个极简的终端 UI 框架，支持差分渲染、同步输出（几乎无闪烁），以及带自动补全的编辑器和 markdown 渲染等组件。
- **[pi-coding-agent](https://github.com/badlogic/pi-mono/tree/main/packages/coding-agent)**：把这一切组合起来的实际 CLI，包含会话管理、自定义工具、主题和项目上下文文件。

我贯穿始终的哲学是：我不需要的东西就不做。而我需要的东西并不多。

## pi-ai 与 pi-agent-core

我不会用这个包的 API 细节来烦你，你可以去读 README.md。这里我想记录的是我在创建统一 LLM API 时遇到的问题以及我的解决方案。我并不是说我的方案是最好的，但它们在各种智能体和非智能体 LLM 项目中一直运转良好。

### 就。是。四。种……API

*（译注：本节标题化用《星际迷航：下一代》中皮卡德舰长的名台词 "There. Are. Four. Lights."（就。是。四。盏。灯。），原文将 "Lights" 截断替换为 "APIs"。）*

要与几乎所有 LLM 提供商对话，实际上只需要说四种 API：OpenAI 的 Completions API、其较新的 Responses API、Anthropic 的 Messages API，以及 Google 的 Generative AI API。

它们的功能都大同小异，所以在其之上构建抽象并非什么火箭科学。当然，有一些提供商特有的怪癖需要照顾。Completions API 尤其如此：几乎所有提供商都说这个"方言"，但每家对它该做什么的理解各不相同。比如 OpenAI 的 Completions API 不支持推理痕迹（reasoning traces），但其他提供商在他们版本的 Completions API 里却支持。llama.cpp、Ollama、vLLM 和 LM Studio 这类推理引擎也是这种情况。

比如，在 `openai-completions.ts` 中：

- Cerebras、xAI、Mistral 和 Chutes 不喜欢 `store` 字段
- Mistral 和 Chutes 用 `max_tokens` 而不是 `max_completion_tokens`
- Cerebras、xAI、Mistral 和 Chutes 不支持用于系统提示词的 `developer` 角色
- Grok 模型不喜欢 `reasoning_effort`
- 不同提供商把推理内容放在不同字段（`reasoning_content` vs `reasoning`）

为了确保所有功能在无数提供商上都能正常工作，pi-ai 有一个相当庞大的测试套件，覆盖图像输入、推理痕迹、工具调用以及你期望 LLM API 具备的其他功能，测试横跨所有受支持的提供商和热门模型。虽然这已经算是尽力而为，但仍无法保证新模型和新提供商开箱即用。

另一个大差异是提供商如何报告 token 以及缓存的读写。Anthropic 的做法最合理，但总体上这就是个"狂野西部"。有的在 SSE 流的开头报告 token 数，有的只在结尾报告，一旦请求被中止，准确的成本追踪就无从谈起。更糟的是，你无法提供一个唯一 ID 去与他们的计费 API 关联，从而弄清你的哪些用户消耗了多少 token。所以 pi-ai 的 token 和缓存追踪是尽力而为的：个人使用足够好，但如果你的服务有终端用户在消耗 token，它并不适合精确计费。

特别"表扬"一下 Google：时至今日他们似乎仍不支持工具调用流式输出，这非常 Google。

pi-ai 也可以在浏览器中运行，这对构建 Web 界面很有用。一些提供商通过支持 CORS 让这件事变得特别容易，具体来说就是 Anthropic 和 xAI。

### 上下文交接

跨提供商的上下文交接是 pi-ai 从设计之初就内置的特性。由于每家提供商追踪工具调用和思考痕迹的方式各不相同，这只能是尽力而为。例如，如果你在会话中途从 Anthropic 切换到 OpenAI，Anthropic 的思考痕迹会被转换为助手消息内的内容块，用 `<thinking></thinking>` 标签界定。这是否合理见仁见智，因为 Anthropic 和 OpenAI 返回的思考痕迹其实并不能代表幕后真实发生的事情。

这些提供商还会在事件流中插入签名的数据块（blob），你必须在后续包含相同消息的请求中原样回放它们。即使在同一提供商内切换模型也是如此。这导致幕后需要一个相当繁琐的抽象与转换管线。

我很高兴地报告，pi-ai 的跨提供商上下文交接以及上下文序列化/反序列化工作得相当好：

```ts
// 在会话中途切换提供商
const newContext = await convertContext(context, "openai-completions");

// 序列化 / 反序列化（用于存储）
const serialized = JSON.stringify(context);
const deserialized = Context.deserialize(JSON.parse(serialized));
```

### 我们生活在一个多模型世界

说到模型，我希望在 `getModel` 调用中能用类型安全的方式指定模型。为此我需要一个能转成 TypeScript 类型的模型注册表。我把 OpenRouter 和 models.dev（opencode 团队创建的，非常感谢，超级有用）的数据解析进 `models.generated.ts`，其中包括 token 成本以及图像输入、思考支持等能力标记。

而如果需要添加注册表里没有的模型，我希望类型系统能让创建新模型变得容易。这在处理自托管模型、尚未进入 models.dev 或 OpenRouter 的新模型，或尝试某个冷门 LLM 提供商时特别有用：

```ts
import { getModel, type Model } from "@mariozechner/pi-ai";

const myNewModel: Model<"openai-completions"> = {
	id: "my-new-model",
	baseUrl: "https://my-provider.com/v1",
	api: "openai-completions",
	reasoning: false,
	input: ["text"],
	cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
	contextWindow: 128000,
	maxTokens: 16384,
};
```

很多统一 LLM API 完全无视中止请求的能力。如果你想把 LLM 集成到任何生产系统中，这是完全不可接受的。很多统一 LLM API 也不返回部分结果，这相当荒谬。pi-ai 从一开始就被设计为在整个管线中支持中止，包括工具调用。工作方式如下：

```ts
const abortController = new AbortController();

const stream = await stream(model, context, {
	apiKey,
	signal: abortController.signal,
});

// 随时中止，已生成的部分结果仍然可用
abortController.abort();
```

### 结构化的分离式工具结果

还有一种抽象我在任何统一 LLM API 里都没见过：把工具结果拆成交给 LLM 的部分和用于 UI 展示的部分。LLM 部分通常只是文本或 JSON，不一定包含你想在 UI 中展示的全部信息；而解析文本形式的工具输出再重组给 UI 展示，体验也极差。pi-ai 的工具实现允许同时返回给 LLM 的内容块和用于 UI 渲染的独立内容块。工具还可以返回图像等附件，并以相应提供商的原生格式附加。工具参数通过 TypeBox schema 和 AJV 自动校验，校验失败时会给出详细的错误信息：

```ts
import { createTool, Type } from "@mariozechner/pi-ai";

const myTool = createTool({
	name: "my_tool",
	label: "My Tool",
	description: "Does something useful",
	parameters: Type.Object({
		input: Type.String({ description: "The input" }),
	}),
	execute: async (args, signal) => {
		return {
			// 交给 LLM 的内容
			content: [{ type: "text", text: `Result: ${args.input}` }],
			// 用于 UI 渲染的独立内容
			display: {
				title: "My Tool",
				output: [{ type: "text", text: `Pretty display: ${args.input}` }],
			},
		};
	},
});
```

目前还缺的是工具结果的流式传输。设想一个 bash 工具，你想在 ANSI 序列到来时就实时显示它们——目前还做不到，但修复很简单，终究会进入这个包。

工具调用流式传输期间的增量 JSON 解析对好的 UX 至关重要。当 LLM 流式输出工具调用参数时，pi-ai 会渐进式地解析它们，让你在调用完成前就能在 UI 中展示部分结果。比如，当智能体重写一个文件时，你可以实时展示流入的 diff。

### 极简的智能体脚手架

最后，pi-ai 提供了一个智能体循环来处理完整的编排：处理用户消息、执行工具调用、把结果回传给 LLM，然后重复，直到模型产出不带工具调用的响应。这个循环还通过回调支持消息排队：每一轮结束后，它会询问排队的消息，并在下一次助手响应之前注入。循环会为一切发出事件，让构建响应式 UI 变得容易。

这个智能体循环不允许你指定最大步数或你在其他统一 LLM API 里能找到的类似旋钮。我从没找到过这种需求的使用场景，那为什么要加？循环就是一直转，直到智能体说自己完成了。不过在循环之上，pi-agent-core 提供了一个 `Agent` 类，带有真正有用的东西：状态管理、简化的事件订阅、两种模式的消息排队（逐条或一次性全部）、附件处理（图像、文档），以及一个传输抽象，让你既能直接运行智能体，也能通过代理运行。

我对 pi-ai 满意吗？大体上是的。和任何统一 API 一样，由于抽象泄漏（leaky abstractions），它永远不可能完美。但它已经被七个不同的生产项目使用，一直服务得非常好。

为什么要自己造这个轮子而不用 Vercel AI SDK？[Armin 的博文](https://arminronacher.github.io/2025/ai-frameworks-and-the-limits-of-language/)与我的经历如出一辙。直接构建在提供商 SDK 之上给了我完全的控制权，让我能完全按自己的意愿设计 API，表面积也小得多。Armin 的博客对"为什么要自己造"有更深入的论述，去读读吧。

## pi-tui

我是在 DOS 时代长大的，终端用户界面就是陪伴我童年的东西。从 Doom 花哨的安装程序到 Borland 的产品，TUI 一直陪着我，直到 90 年代末。而当我终于切换到 GUI 操作系统时，我他妈简直高兴坏了。虽然 TUI 基本上可移植、易于流式传输，但它们在信息密度方面很糟糕。话虽如此，我认为为 pi 先做一个终端用户界面是最合理的，以后随时想加 GUI 都可以再装上。

那为什么要自己写 TUI 框架？我研究过 Ink、Blessed、OpenTUI 等替代品。我确信它们各有各的好，但我绝对不想像写 React 应用那样写我的 TUI。Blessed 似乎基本无人维护了，OpenTUI 则明确表示尚未达到生产可用。再说，在 Node.js 之上写自己的 TUI 框架听起来就是个有趣的小挑战。

### 两种 TUI

写终端用户界面本身不算什么火箭科学，你只需要选择你的"毒药"（两害相权取其轻）。基本上有两种做法。一种是接管终端视口（terminal viewport，即你实际能看到的终端内容部分），把它当作像素缓冲区来对待。只不过这里不是像素，而是包含字符的单元格，每个字符有背景色、前景色以及斜体、粗体等样式。我把这类称为全屏 TUI。Amp 和 opencode 用的就是这种。

缺点是你会失去回滚缓冲区（scrollback buffer），这意味着你得自己实现搜索功能。你也会失去滚动功能，这意味着你得自己在视口内模拟滚动。虽然这不难实现，但这意味着你得重新实现终端模拟器已经提供的所有功能。尤其是鼠标滚动，在这种 TUI 里总感觉有点不对劲。

第二种做法是像任何 CLI 程序一样直接向终端写入，把内容追加到回滚缓冲区，只是偶尔把"渲染光标"在可见视口内往上移一点，以重绘动画加载指示器或文本编辑框之类的东西。实际没这么简单，但大概就是这个意思。Claude Code、Codex 和 Droid 用的就是这种。

编码智能体有个很棒的性质：它们本质上就是一个聊天界面。用户写一段提示词，然后是智能体的回复、工具调用及其结果。一切都呈漂亮的线性排列，这天然适合与"原生"终端模拟器协作。你可以使用所有内置功能，比如自然的滚动和回滚缓冲区内搜索。这也在一定程度上限制了 TUI 能做的事，我觉得这反而有魅力——约束造就极简的程序，只做该做的事，没有多余的浮华。这就是我为 pi-tui 选择的方向。

### 保留模式 UI

如果你做过 GUI 编程，大概率听说过保留模式（retained mode）与立即模式（immediate mode）。在保留模式 UI 中，你构建一棵跨帧持续存在的组件树，每个组件知道如何渲染自己，并且在没有变化时可以缓存其输出。在立即模式 UI 中，你每一帧都从头重绘一切（尽管实践中立即模式 UI 也会做缓存，否则它们早就崩溃了）。

pi-tui 采用简单的保留模式。`Component` 只是一个带有 `render(width)` 方法的对象，该方法返回一个字符串数组（水平方向适配视口的行，带 ANSI 转义码用于颜色和样式），以及一个可选的用于键盘输入的 `handleInput(data)` 方法。`Container` 持有一个垂直排列的组件列表并收集它们渲染的所有行。`TUI` 类本身就是一个容器，负责统筹一切。

当 TUI 需要更新屏幕时，它会请求每个组件进行渲染。组件可以缓存自己的输出：一条已经流式完毕的助手消息不需要每次都重新解析 markdown、重新渲染 ANSI 序列，直接返回缓存的行即可。容器从所有子组件收集行。TUI 汇总所有这些行，把它们与上一次组件树渲染的行进行比较。它保留着某种形式的后备缓冲区（backbuffer），记住回滚缓冲区里写过什么。

然后它只重绘变化的部分，用的是一个我称为差分渲染（differential rendering）的方法。我起名字的水平很糟糕，这很可能有个正式名称。

### 差分渲染

这里有一个简化的演示，说明了具体哪些内容会被重绘：

![差分渲染演示](https://mariozechner.at/media/diffrender.gif)

算法很简单：

1. **首次渲染**：直接把所有行输出到终端。
2. **宽度变化**：完全清屏并重新渲染一切（因为软换行位置发生了变化）。
3. **常规更新**：找到第一行与屏幕上不同的行，把光标移动到那一行，从那里重绘到末尾。

有一个坑：如果第一处变化发生在可见视口之上（用户向上滚动了），我们就必须完全清屏并重新渲染。终端不允许你写入视口上方的回滚缓冲区。

为了防止更新过程中的闪烁，pi-tui 把所有渲染包裹在同步输出转义序列（`CSI ?2026h` 和 `CSI ?2026l`）中。这告诉终端把所有输出缓冲起来并原子性地显示。大多数现代终端都支持。

效果如何？闪烁多少？在任何能力足够的终端里，比如 Ghostty 或 iTerm2，这运转得非常出色，你完全看不到闪烁。在没那么幸运的终端实现里，比如 VS Code 的内置终端，你还是会在某些时候看到一些闪烁，具体取决于一天中的时段、你的显示器尺寸、窗口大小等等。鉴于我已经非常习惯 Claude Code，我没有再花更多时间去优化它。VS Code 里那点闪烁让我感到熟悉，否则反而不习惯。而且它仍然比 Claude Code 闪烁得少。

这种做法有多浪费？我们存着相当于整个回滚缓冲区大小的历史渲染行，而且每次 TUI 被要求渲染自己时都要重新渲染所有行。上面描述的缓存缓解了这个问题，所以重新渲染不算什么大事。我们仍然要做大量的行与行比较。现实点说，在任何不到 25 年历史的电脑上，无论性能还是内存占用（超大会话也就几百 KB）都不是问题。谢谢 V8。作为回报，我得到了一个简单到死的编程模型，让我能快速迭代。

## pi-coding-agent

我不需要解释一个编码智能体框架应该有哪些功能。pi 自带了你从其他工具习惯的大多数舒适配置：

- 运行于 Windows、Linux 和 macOS（或任何有 Node.js 运行时和终端的环境）
- 多提供商支持，会话中途可切换模型
- 会话管理，支持继续、恢复和分支
- 项目上下文文件（AGENTS.md），从全局到项目层级加载
- 常用操作的斜杠命令
- 自定义斜杠命令，以 markdown 模板形式并支持参数
- Claude Pro/Max 订阅的 OAuth 认证
- 通过 JSON 配置自定义模型和提供商
- 可自定义主题，支持热重载
- 编辑器支持模糊文件搜索、路径补全、拖拽和多行粘贴
- 智能体工作时的消息排队
- 支持视觉模型使用图像
- 会话导出为 HTML
- 通过 JSON 流式输出和 RPC 模式的无头（headless）运行
- 完整的成本和 token 追踪

想要完整清单请读 [README](https://github.com/badlogic/pi-mono/tree/main/packages/coding-agent)。更有意思的是 pi 在哲学和实现上与其他框架的分歧之处。

### 极简系统提示词

系统提示词如下：

```
你是一位专业的编程助手。你通过读取文件、执行命令、编辑代码和编写新文件来帮助用户完成编程任务。

可用工具：
- read：读取文件内容
- bash：执行 bash 命令
- edit：对文件做精准编辑
- write：创建或覆盖文件

准则：
- 用 bash 执行 ls、grep、find 等文件操作
- 编辑前先用 read 检查文件内容
- 用 edit 做精准修改（oldText 必须完全匹配）
- write 仅用于新文件或完整重写
- 总结你的工作时直接输出纯文本——不要用 cat 或 bash 来展示你做了什么
- 回复要简洁
- 处理文件时清晰地展示文件路径

文档：
- 你自己的文档（包括自定义模型配置和主题创建）位于：/path/to/README.md
- 当用户询问功能、配置或设置时阅读它，尤其是当用户要求你添加自定义模型或提供商、或创建自定义主题时。
```

（译注：原文提示词为英文，此处为中文译意。）

就这样。唯一会在底部注入的是你的 AGENTS.md 文件——既有适用于所有会话的全局文件，也有存放在项目目录中的项目专属文件。这就是你按自己喜好定制 pi 的地方，你甚至可以整体替换系统提示词。对比一下，比如 [Claude Code 的系统提示词](https://github.com/AnthropicClaude/claude-code-system-prompts)、[Codex 的系统提示词](https://github.com/openai/codex)，或者 [opencode 的模型专属提示词](https://github.com/sst/opencode)（其中的 Claude 版本是它们照抄的原始 Claude Code 提示词的删减版）。

你可能觉得这疯了。模型很可能对其原生的编码框架有过训练，所以像 opencode 那样使用原生系统提示词或接近它的东西似乎最理想。但事实是，所有前沿模型都经历了多得吓人的强化学习（RL）训练，它们天生就知道编码智能体是什么。看起来并不需要一万 token 的系统提示词——后面的基准测试部分会证明这一点，而我过去几周专用 pi 的亲身经历也印证了这一点。Amp 虽然照搬了原生系统提示词的部分内容，但用它自己的提示词似乎也运转得很好。

### 极简工具集

工具定义如下：

```
read
  读取文件内容。支持文本文件和图像（jpg、png、gif、webp）。图像作为附件发送。
  文本文件默认读取前 2000 行。更大的文件可使用 offset/limit。
  - path：要读取的文件路径（相对或绝对）
  - offset：起始读取的行号（从 1 开始）
  - limit：最多读取的行数

write
  将内容写入文件。文件不存在则创建，存在则覆盖。自动创建父目录。
  - path：要写入的文件路径（相对或绝对）
  - content：要写入的内容

edit
  通过精确文本替换来编辑文件。oldText 必须完全匹配（包括空白字符）。
  用于精准的外科手术式修改。
  - path：要编辑的文件路径（相对或绝对）
  - oldText：要查找并替换的精确文本（必须完全匹配）
  - newText：用于替换的新文本

bash
  在当前工作目录执行 bash 命令。返回 stdout 和 stderr。可以秒为单位提供可选超时。
  - command：要执行的 bash 命令
  - timeout：超时秒数（可选，默认：无超时）
```

（译注：原文工具定义为英文，此处为中文译意。）

还有一些只读工具（grep、find、ls），如果你想限制智能体不得修改文件或执行任意命令可以使用。默认情况下它们是禁用的，智能体只拿到上面四个工具。

事实证明，一个高效的编码智能体只需要这四个工具。模型知道怎么用 bash，并且在 read、write、edit 这类相似输入 schema 的工具上受过训练。对比一下 [Claude Code 的工具定义](https://github.com/AnthropicClaude/claude-code-system-prompts)或 [opencode 的工具定义](https://github.com/sst/opencode)（后者明显源自 Claude Code：同样的结构、同样的示例、同样的 git 提交流程）。值得一提的是，Codex 的工具定义和 pi 一样极简。

pi 的系统提示词和工具定义加起来不到 1000 个 token。

### 默认 YOLO 模式

*（译注：YOLO，"You Only Live Once"。YOLO 模式指不做任何权限确认、放手让智能体直接执行所有操作的运行方式。）*

pi 以完全的 YOLO 模式运行，并假定你知道自己在干什么。它对你的文件系统拥有不受限制的访问权，可以在没有权限检查或安全护栏的情况下执行任何命令。文件操作和命令没有权限提示。没有用 Haiku 预先检查 bash 命令是否包含恶意内容。完整的文件系统访问。能以你的用户权限执行任何命令。

看看其他编码智能体的安全措施，它们大多是安全表演（security theater）。只要你的智能体能写代码、能运行代码，基本上就大势已去。想防止数据外泄，唯一的办法是切断智能体运行环境的所有网络访问，而这会让智能体基本废掉。另一种办法是域名白名单，但这也能通过其他手段绕过。

[Simon Willison 就这个问题写过大量文章](https://simonwillison.net/2023/Apr/11/dual-llm-pattern/)。他的"双 LLM"（dual LLM）模式试图应对混淆代理人攻击（confused deputy attack）和数据外泄，但连他自己都承认"这个方案相当糟糕"，而且引入了巨大的实现复杂度。核心问题依然存在：如果一个 LLM 能使用既能读取隐私数据又能发起网络请求的工具，那你就是在和攻击面玩"打地鼠"游戏。

既然我们无法解决"读数据、执行代码、联网"这个三重能力难题，pi 干脆认了。反正大家为了干点正经活儿都在用 YOLO 模式，何不把它设为默认且唯一的选项？

默认情况下，pi 没有网络搜索或抓取工具。不过它可以用 `curl` 或从磁盘读文件，这两者都为提示词注入攻击提供了充足的攻击面。文件或命令输出中的恶意内容可以影响其行为。如果你对完全访问感到不安，可以在容器中运行 pi；如果你需要（虚假的）护栏，那就用别的工具吧。

### 没有内置待办清单

pi 现在不支持、将来也不会支持内置待办清单。以我的经验，待办清单通常给模型带来的困惑多于帮助。它们增加了模型必须跟踪和更新的状态，从而引入了更多出错机会。

如果你需要任务跟踪，把它做成外部状态，写进文件：

```markdown
# TODO.md

- [x] 实现用户认证
- [x] 添加数据库迁移
- [ ] 编写 API 文档
- [ ] 添加限流
```

智能体可以按需读取和更新这个文件。用复选框记录哪些完成了、哪些还没做。简单、可见、尽在你掌控。

### 没有计划模式

pi 现在不会有、将来也不会有内置计划模式。让智能体和你一起把问题想清楚、而不修改文件或执行命令，一般来说就足够了。

如果你需要跨会话的持久化计划，把它写进文件：

```markdown
# PLAN.md

## 目标
重构认证系统以支持 OAuth

## 方案
1. 调研 OAuth 2.0 流程
2. 设计 token 存储结构
3. 实现授权服务器端点
4. 更新客户端登录流程
5. 添加测试

## 当前步骤
正在做第 3 步——授权端点
```

智能体在工作时可以读取、更新和引用这份计划。与只存在于单个会话中的临时计划模式不同，基于文件的计划可以跨会话共享，还能随代码一起版本化。

有意思的是，Claude Code 现在有个计划模式，本质上就是只读分析，而且它最终也会往磁盘写一个 markdown 文件。而且不用批准一大堆命令调用，你基本没法用计划模式——因为不批准的话，计划根本没法做。

pi 的不同之处在于我对一切拥有完整的可观测性。我能看到智能体实际查看了哪些资料、完全漏掉了哪些。在 Claude Code 里，编排的 Claude 实例通常会生成一个子智能体，而你对那个子智能体在干什么一无所知。pi 里我能立刻看到 markdown 文件，还能和智能体协作编辑它。简言之，规划需要可观测性，而 Claude Code 的计划模式给不了我。

如果你必须在规划期间限制智能体，可以通过 CLI 指定它能使用哪些工具：

```
pi --tools read,grep,find,ls
```

这给你一个只读模式，用于探索和规划，智能体不能修改任何东西、也不能运行 bash 命令。不过你用起来不会开心的。

### 不支持 MCP

pi 现在不支持、将来也不会支持 MCP。我[对此写过很多](https://mariozechner.at/posts/2025-07-21-mcp-llm-api-overengineering/)，长话短说：MCP 服务器对大多数用例来说都是杀鸡用牛刀，而且带来可观的上下文开销。

流行的 MCP 服务器，如 Playwright MCP（21 个工具，13.7k token）或 Chrome DevTools MCP（26 个工具，18k token），会在每个会话把它们的全部工具描述倾倒进你的上下文。还没开始干活，上下文窗口就没了 7-9%。而其中很多工具在某个会话里你根本用不到。

替代方案很简单：构建带 README 文件的 CLI 工具。智能体需要用某个工具时才去读它的 README，只在必要时才付出 token 成本（渐进式披露），并且能用 bash 调用工具。这种做法可组合（管道输出、串联命令）、易扩展（加个脚本就行）、省 token。

如果你实在必须用 MCP 服务器，可以看看 Peter Steinberger 的 [mcporter](https://github.com/steipete/mcporter) 工具，它把 MCP 服务器包装成 CLI 工具。

### 没有后台 bash

pi 的 bash 工具同步运行命令。没有内置的方式启动开发服务器、在后台跑测试，或在命令还在运行时与 REPL 交互。

这是有意为之。后台进程管理会增加复杂度：你需要进程跟踪、输出缓冲、退出时清理，以及向运行中的进程发送输入的手段。Claude Code 用它的后台 bash 功能处理了一部分，但可观测性很差（这是 Claude Code 的通病），而且强迫智能体跟踪运行中的实例，却不提供查询它们的工具。在早期版本的 Claude Code 中，智能体在上下文压缩后会忘记所有后台进程且无法查询，你只能手动杀掉它们。这个问题后来修复了。

用 tmux 代替。下面是 pi 在 LLDB 中调试一个崩溃的 C 程序：

[演示视频](https://mariozechner.at/media/tmux.mp4)

这可观测性如何？同样的方法适用于长时间运行的开发服务器、监视日志输出和类似用例。而且如果你想的话，可以通过 tmux 进入上面的那个 LLDB 会话，和智能体一起协同调试。Tmux 还提供一个 CLI 参数列出所有活动会话。多贴心。

后台 bash 根本没必要。Claude Code 也能用 tmux，你知道吧。Bash 就是你的全部所需。

### 没有子智能体

pi 没有专门的子智能体工具。当 Claude Code 需要做复杂的事时，它常常生成一个子智能体来处理部分任务。你对子智能体在干什么毫无可见性——黑盒里的黑盒。智能体之间的上下文传递也很差：编排智能体决定传给子智能体什么初始上下文，而你对此基本没有控制权。如果子智能体犯了错，调试会很痛苦，因为你看不到完整对话。

如果你需要 pi 生出自己，让它通过 bash 运行自己就行。你甚至可以让它在 tmux 会话中生成自己，从而获得完整的可观测性以及直接与那个子智能体交互的能力。

![子智能体](https://mariozechner.at/media/subagent.jpeg)

但更重要的是：改进你的工作流，至少是那些纯粹为了收集上下文的工作流。人们在会话中使用子智能体，以为这样节省上下文空间——这倒是真的。但这是对子智能体的错误理解。在会话中途使用子智能体收集上下文，是你没有提前规划的信号。如果你需要收集上下文，先在独立的会话里做。产出一个工件（artifact），之后在一个全新会话里使用它，给你的智能体所需的全部上下文，而不用让工具输出污染它的上下文窗口。这个工件对下一个功能也有用，而且你拥有完整的可观测性和可操纵性——这在收集上下文时很重要。

因为与普遍看法相反，模型仍然不擅长找齐实现新功能或修复 bug 所需的全部上下文。我把这归因于模型被训练成只读文件的部分内容而不是完整文件，所以它们不愿通读一切。这意味着它们会漏掉重要上下文，看不全正确完成任务所需的信息。

看看 pi-mono 的 issue 跟踪器和 pull request 就知道了。很多被关闭或要求修改，因为智能体没法完全理解需求。这不是贡献者的错——我真心感激他们，因为即使不完整的 PR 也能帮我更快前进。这只能说明我们太信任自己的智能体了。

我并非完全否定子智能体，它们有合理的使用场景。我最常用的是代码审查：我让 pi 通过自定义斜杠命令、带着代码审查提示词生成自己，然后取回输出。

```
---
description: Run a code review subagent
---
通过 bash 把你自己生成为子智能体，来审查这段代码：$@

使用 `pi --print` 加上相应的参数。如果用户指定了模型，
相应地使用 `--provider` 和 `--model`。

给子智能体的提示词应要求它审查代码中的：
- Bug 和逻辑错误
- 安全问题
- 错误处理缺口

你自己不要去读代码，让子智能体来做。

汇报子智能体的发现。
```

下面是我如何用它审查 GitHub 上的 pull request：

[演示视频](https://mariozechner.at/media/subagent.mp4)

用一段简单的提示词，我就能选择要审查的具体内容和要用的模型，想的话甚至可以设置思考等级。我还可以把完整的审查会话保存到文件，之后在另一个 pi 会话里进去看。或者我可以声明这是个临时会话、不该存盘。这一切都被翻译成一段提示词，主智能体读取后据此通过 bash 再次执行自己。虽然我对子智能体的内部运作没有完整可观测性，但我对它的输出有完整可观测性。其他框架并不真正提供这一点，这让我百思不得其解。

当然，这多少是个演示性的用例。实际操作中，我只会开一个新的 pi 会话，让它审查那个 pull request，可能先在本地拉一个分支。看到它的初步审查后，我给出自己的意见，然后我们一起改到满意为止。这就是我用来避免合并垃圾代码的工作流。

在我的书上，生成多个子智能体并行实现各种功能是一种反模式，行不通——除非你不在乎你的代码库沦为一堆垃圾。

另外请注意 Terminus 2 在排行榜上的排名。Terminus 2 是 Terminal-Bench 团队自己的极简智能体，它只是给模型一个 tmux 会话。模型以文本形式向 tmux 发送命令，自己解析终端输出。没有花哨的工具，没有文件操作，只有原始的终端交互。它在与工具复杂得多的智能体较量中毫不逊色，而且能配合多种多样的模型。这是"极简方案可以做得一样好"的又一例证。

## 总结

基准测试结果很好笑，但真正的考验还得靠日常使用（布丁好不好，吃了才知道）。而在我的日常工作中，pi 表现令人钦佩。Twitter 上到处是关于上下文工程的帖子和博客，但我觉得我们现有的框架没有一个真正让你做上下文工程。pi 是我为自己打造一个尽可能由我掌控的工具的尝试。

我对 pi 目前所处的状态相当满意。还有一些我想加的功能，比如上下文压缩（compaction）或工具结果流式传输，但我觉得自己个人需要的不多了。缺压缩对我个人来说不是问题。不知为何，我能把我和智能体之间数百轮对话塞进单个会话，这在 Claude Code 里不做压缩是做不到的。

话虽如此，我欢迎贡献。但和我所有开源项目一样，我倾向于独断式管理。这是我这些年从大项目里痛苦学到的教训。如果我关闭了你提交的 issue 或 PR，希望你别往心里去，我也会尽力说明原因。我只想保持这个项目专注和可维护。如果 pi 不符合你的需求，我恳请你 fork 它，我是认真的。而如果你做出了更符合我需求的东西，我会欣然加入你的努力。

我认为上面的一些经验同样适用于其他框架。如果对你奏效，告诉我一声。
